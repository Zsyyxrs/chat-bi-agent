## chat-bi-agent · 银行业务人员自助 BI 智能体 — 架构设计 v2

### 一、项目定位

**项目名**：`chat-bi-agent`

**一句话定位**：

> 面向银行业务人员的对话式 BI 智能体——把"提需求→排期→开发报表→看报表→找数→人工归因"的传统链路，压缩成"一句话提问→直接出数→自动归因→可追问"。

**核心交付用户**：银行内部业务人员（支行业务经理、产品经理、风险分析师、运营、营销人员），**不是数据开发、不是 BI 工程师**。

#### 1.1 三个核心痛点（用户直接定义）

| #  | 业务痛点                             | 当前流程                                         | chat-bi-agent 解法                                               |
| -- | ------------------------------------ | ------------------------------------------------ | ---------------------------------------------------------------- |
| P1 | BI 报表开发流程长                    | 业务提需求→BI 排期（数周）→开发→上线          | 业务人员直接提问→指标平台 + NL2SQL 实时出数                     |
| P2 | 报表上线后业务还要"在报表里找具体数" | 看大报表→筛选→定位单元格→截图发群             | 自然语言精准取数：「上周深圳分行个人房贷新增多少」→ 直接给数+图 |
| P3 | 归因分析缺失，只能看到"是什么"       | 数字异常→拉数据→人工拆维度→Excel 透视→猜原因 | 归因 Agent 自动做多维下钻 + 同环比 + 贡献度 + 异常检测           |

#### 1.2 由此可衍生解决的业务问题（推断）

- **跨部门口径不一致**：零售部和风险部都说"逾期率"，但口径不同 → 指标平台统一口径
- **新人上手慢**：新员工不熟悉报表系统 → 自然语言提问替代菜单导航
- **临时性分析需求被压抑**："这个想看一下但不值得排期"的需求 → 自助即时回答
- **会议汇报准备耗时**：周/月度复盘前要拼数 → 一句话生成洞察卡片+图表
- **数据口径漂移**：报表口径几年没人维护 → 集中式指标定义+版本管理
- **风险事件复盘慢**：可疑交易/异常波动出现后要回溯 → 归因 Agent 加速根因定位
- **不会写 SQL 的 leader 被卡脖子**：要等下属拉数 → 直接问

### 二、产品形态（业务视角先行）

#### 2.1 三个核心场景

**场景 A：精准取数（替代"翻报表找数"）**

```
业务：上周深圳分行个人住房按揭贷款新增金额是多少？
Agent：
  - 数字：¥ 3.27 亿（环比 ↑ 12.4%）
  - 一句话解读：高于近 4 周均值，主要由龙华支行贡献
  - 可追问：[按支行拆解] [对比上月] [看趋势图]
```

**场景 B：多步分析（替代"BI 开发新报表"）**

```
业务：帮我看一下本月信用卡分期业务的情况
Agent：
  - 自动拆解为：办理笔数、办理金额、平均期数、分期手续费、坏账率
  - 输出洞察卡片（5 个核心指标 + 趋势图 + 异动标注）
  - 末尾给出 3 个建议追问
```

**场景 C：归因分析（核心差异化，解决 P3）**

```
业务：本月零售存款余额为什么下降了？
Agent（归因引擎自动执行）：
  1. 确认事实：环比 -2.3%，同比 -0.8%，主要在 5/15 后开始下滑
  2. 维度下钻：
     - 按分行：上海分行贡献 68% 的下滑
     - 按客群：高净值客户（AUM>500w）贡献 81% 的下滑
     - 按产品：活期 -5.1%，定期 +1.2%（活期资金流出）
  3. 假设验证：是否对应某只理财产品到期？→ 关联到 5/14 到期的"安鑫 90 天"
  4. 结论：上海分行高净值客户的活期存款，因「安鑫 90 天」到期未续作而流出
  5. 建议追问：[流出资金去向] [对比上一期到期续作率]
```

#### 2.2 业务人员侧 UX 关键决策

| 决策                   | 设计                                                   | 理由                             |
| ---------------------- | ------------------------------------------------------ | -------------------------------- |
| 不让用户对着空白输入框 | 首页提供「指标卡片广场」+「我的常用问题」+「示例问题」 | 业务人员不知道能问什么           |
| 每个回答都带可追问按钮 | LLM 自动生成 3 个相关追问                              | 降低连续对话门槛                 |
| 数字必带"可信度标识"   | 用了哪个指标定义 / 命中了哪些表 / SQL 可点开           | 银行场景对错误零容忍，必须可追溯 |
| 不会的问题主动说"不会" | Planner 判断为 `unsupported` 时给出引导              | 比胡说强一百倍                   |
| 报表不只是表格         | 默认输出 = 数字 + 图表 + 一句话解读 + 追问             | 解决 P2，不让用户再去"找数"      |
| 个人空间 / 团队空间    | 业务人员可以收藏问题、组成自己的"我的看板"             | 替代部分固定报表                 |

### 四、核心模块设计（重点写新增/重构的）

#### Module 1: Planner + Router（意图识别与路由）

**职责**：把业务人员的口语问题分类到三条主路径

```python
@dataclass
class Intent:
    route: Literal["precise_lookup", "multi_step_analysis",
                   "root_cause_analysis", "unsupported"]
    entities: Dict[str, Any]   # 时间/分行/客群/产品 等抽取
    sub_questions: List[str]   # 多步场景下拆解
    requires_clarification: bool
    clarification_prompt: Optional[str]
```

**关键设计**：

- 业务人员问题里通常缺时间维度（"最近怎么样"）→ 主动追问，不要瞎猜
- 含「为什么 / 原因 / 下降 / 异常 / 归因」→ 路由到 RCA
- 不在数据域内（"今天天气") → 礼貌拒绝并引导

#### Module 2: 指标平台（Headless Metric Layer）— **解决 P1 的核心**

**为什么独立成"平台"而不是"层"**：

- 银行 BI 开发慢的根因之一是「每个报表都重新定义口径」
- 指标平台让业务自己审定指标 → 之后所有问答自动复用
- 是绕过传统报表开发流程的关键基础设施

**能力清单**：

```yaml
# metrics/retail_deposit.yaml
metric:
  id: retail_deposit_balance
  name: 零售存款余额
  owner: 零售业务部
  version: 2.1
  effective_date: 2026-01-01
  aliases: [零售存款, 个人存款余额, retail_deposit]
  business_definition: |
    截止某日，所有零售客群（个人客户）的活期+定期+大额存单余额之和。
    不含对公存款、不含同业存款。
  sql_template: |
    SELECT SUM(balance)
    FROM ads_account_daily_snapshot
    WHERE snapshot_date = '{date}'
      AND customer_segment = 'RETAIL'
      AND account_type IN ('CURRENT', 'FIXED', 'CD')
  dimensions:
    - branch_id          # 分行
    - sub_branch_id      # 支行
    - customer_tier      # 客户分层
    - product_id
  drill_down_priority: [branch_id, customer_tier, product_id]
  related_metrics:
    - retail_deposit_inflow      # 流入
    - retail_deposit_outflow     # 流出
    - retail_deposit_yoy         # 同比
  governance:
    approved_by: 零售部数据治理委员会
    review_cycle: quarterly
    lineage_url: /lineage/retail_deposit_balance
```

**运行时流程**：

1. 用户问 → Metric Matcher 用向量检索 + 别名表匹配指标
2. 命中指标 → 直接用 SQL 模板填参，**不让 LLM 重写 SQL**（口径稳定性最重要）
3. 未命中 → 走 NL2SQL 兜底路径（带提示「此结果未走指标库，请人工核对」）

**衍生价值**：

- 业务方自己维护 YAML（带 Git 流程）= **业务参与的指标治理**
- 指标库可独立暴露 API，给其他系统调用 → 项目天然有平台属性

#### Module 3: Schema Linker（沿用 v1，做轻量加强）

保留原有三层召回（Metric → Table → Column），重点强化：

- **业务术语词典**：把"个贷"="个人贷款"="个人信贷"做同义词扩展
- **行权 schema 视图**：根据当前用户权限只召回他能看的表

#### Module 4: SQL Generator + Validator + Executor

沿用 v1，但 Validator 额外加银行场景检查：

- **禁查表**清单（员工薪酬、客户身份证号原值等）
- **必须脱敏列**清单（手机号、卡号、身份证）→ 强制套脱敏函数
- **大表必带分区过滤**（防止扫全表拖垮生产库）
- **执行账号权限**与当前业务人员严格对齐（行级权限下推到 DB）

#### Module 5: 归因 Agent (RCA)  — **解决 RCA 的核心**

**职责**：当用户问"为什么 X 下降/上升/异常"时，自动完成根因分析。

##### 5.1 设计原则（必须先看）

> **本模块不是"用大模型做归因"，而是"用确定性算法做数值分析 + LLM 做编排与叙述"的混合架构（Hybrid AI）。**

调研当前主流方案（ThoughtSpot Spotter、阿里 Quick BI 智能小Q、AIOps 学术界）后形成的三条铁律：

| 原则                           | 含义                                                             | 反例（绝对禁止）                                     |
| ------------------------------ | ---------------------------------------------------------------- | ---------------------------------------------------- |
| ①**确定性优先**         | 凡是涉及数值计算（贡献度、同环比、显著性）一律走算法和 SQL       | 让 LLM 看一张表然后口算"上海分行贡献了 68%"          |
| ②**可复现 / 可审计**    | 同一个问题在同一份数据上，两次归因结论必须一致；每一步都有 trace | LLM 直接输出"我觉得是因为 XX 产品到期"而没有验证 SQL |
| ③**LLM 只做语义层工作** | 意图理解、算法调度、业务假设生成、自然语言合成 —— 这四件事     | 让 LLM 决定"贡献度阈值是 60% 还是 70%"               |

为什么这么严格——银行场景下一份错误的归因结论可能导致错误的经营决策；监管也要求可追溯。LLM 单独跑归因有三个已知致命问题：算数会错、不可复现、会"自信地胡说"。

##### 5.2 算法工具箱（确定性部分）

按"问题形态 → 推荐算法"组织。所有算法都封装成 LLM 可调用的 tool，输入输出强 schema。

| 算法                         | 适用问题形态                                          | 复杂度 | 引用              | 备注                                              |
| ---------------------------- | ----------------------------------------------------- | ------ | ----------------- | ------------------------------------------------- |
| **同/环比分解**        | "和上周/上月/去年比怎么变了"                          | 低     | 经典 OLAP         | 所有归因的起点                                    |
| **维度下钻**           | "按分行/按客群/按产品拆"                              | 低     | 经典 OLAP         | 用指标 YAML 里的 `drill_down_priority` 控制顺序 |
| **帕累托贡献度**       | "谁贡献了主要波动"                                    | 低     | 经典统计          | 单维度内 TopN 贡献占比                            |
| **Adtributor**         | 加性 KPI、单层多维定位                                | 中     | Microsoft, 2014   | 用 surprise (KL 散度) 找解释力最强的维度组合      |
| **HotSpot**            | 多维加性 KPI、根因可能是组合                          | 高     | 清华 NetMan, 2018 | F-score > 90%，AIOps 工业标准                     |
| **Squeeze**            | 通用多维、根因数量未知                                | 高     | 清华 NetMan, 2019 | 速度 / 效果平衡好，推荐做"重活"                   |
| **iDice**              | 已知根因元素少（1-2 个）                              | 中     | Microsoft         | 元素多了会退化                                    |
| **CMMD**               | 跨指标交叉归因（A 跌是因为 B 跌）                     | 高     | 2022 arXiv        | 进阶能力，二期再考虑                              |
| **STL / Prophet 残差** | 时序异常检测、定位"哪天开始变了"                      | 中     | Facebook / 经典   | 给后续维度归因提供"事件锚点"                      |
| **3σ / IQR**          | 简单阈值异常                                          | 低     | 经典统计          | 兜底用                                            |
| **假设验证**           | "是不是因为 XX 事件"——业务侧给假设，系统跑 SQL 验证 | 低     | 自研              | LLM 提假设、SQL 出证据                            |

**调度策略**（Router 在 RCA Agent 内部用）：

```
if "为什么/原因" + 时间跨度 < 7 天:        → 同/环比 + 帕累托
if "为什么 X 异常" + 时序数据:              → STL/Prophet → 定位时间点 → Adtributor
if "为什么 X 下降" + 维度多 (>3):           → HotSpot 或 Squeeze
if 用户主动给假设（"是不是因为...）:          → 假设验证
默认兜底:                                  → 维度下钻 + 帕累托
```

##### 5.3 LLM × 算法 职责分界（最重要的一张表）

| 步骤                           | 谁来做             | 输入                  | 输出                | 为什么这样分                          |
| ------------------------------ | ------------------ | --------------------- | ------------------- | ------------------------------------- |
| 意图识别（这是归因问题吗）     | **LLM**      | 用户自然语言          | 路由决策            | 算法做不了自然语言理解                |
| 选择算法（用哪种归因）         | **LLM**      | 意图 + 指标元数据     | tool 调用计划       | LLM 适合"按场景挑工具"                |
| 数据获取（取数）               | **算法/SQL** | 算法参数              | DataFrame           | LLM 不能跑 SQL                        |
| 时序异常检测                   | **算法**     | 时序                  | 异常时间点 + 置信度 | 统计模型确定性更高                    |
| 维度贡献度计算                 | **算法**     | DataFrame + 维度      | TopN 贡献度         | LLM 算数不准                          |
| 下钻路径决策                   | **算法**     | 贡献度 + 阈值         | 是否继续下钻        | 用规则更可控（top1 > 60% 就继续）     |
| 业务假设生成（"是不是因为…"） | **LLM**      | 下钻结果 + 行内事件库 | 候选假设列表        | 这是 LLM 真正的价值——把业务先验注入 |
| 假设验证（跑 SQL）             | **算法/SQL** | 假设                  | 验证结果 + 数字     | 必须走 DB                             |
| 结论合成（写出自然语言）       | **LLM**      | 所有事实 + 验证结果   | 业务话术            | LLM 最擅长这一步                      |
| 追问推荐                       | **LLM**      | 结论 + 维度元数据     | 3 个追问按钮        | LLM 适合发散                          |

##### 5.4 执行框架（代码）

```python
class RCAAgent:
    """
    Hybrid RCA：LLM 编排 + 确定性算法计算。
    每个 self.xxx() 都是显式 tool，可被 LLM 通过 function calling 调度。
    """

    def analyze(self, metric: Metric, anomaly: Anomaly,
                context: BusinessContext) -> RCAReport:
        # —— 步骤 1：锚定事实（算法）
        facts = self.fact_anchor(metric, anomaly)

        # —— 步骤 2：时序异常检测（算法）确认变化的时间点
        timepoint = self.anomaly_detector.detect(
            metric.timeseries, method="stl"
        )

        # —— 步骤 3：选择主归因算法（LLM 决策）
        algo_choice = self.llm.choose_algorithm(
            metric=metric, anomaly=anomaly, facts=facts,
            available_tools=["pareto", "adtributor", "hotspot", "squeeze"],
        )
        # 例如：维度多且组合可能性大 → 选 hotspot

        # —— 步骤 4：跑选中的归因算法（算法）
        drill_result = self.run_attribution(algo_choice, metric, timepoint)

        # —— 步骤 5：业务假设生成（LLM，注入行内事件库）
        hypotheses = self.llm.propose_hypotheses(
            metric=metric,
            drill_result=drill_result,
            recent_events=context.recent_events,   # 利率调整/产品到期/活动
            historical_patterns=context.historical_patterns,
        )

        # —— 步骤 6：每个假设跑 SQL 验证（算法/SQL）
        verified = [self.verify_with_sql(h) for h in hypotheses]

        # —— 步骤 7：自然语言合成（LLM）
        narrative = self.llm.synthesize(facts, timepoint, drill_result, verified)

        # —— 全链路 trace 入审计库（合规层强制）
        self.audit.log(metric, facts, algo_choice, drill_result,
                       hypotheses, verified, narrative)

        return RCAReport(
            facts=facts, timepoint=timepoint,
            attribution=drill_result, hypotheses=verified,
            narrative=narrative, trace_id=self.audit.last_trace_id,
        )
```

##### 5.5 关键设计点（保留 + 新增）

- **每一步都可追溯**：事实卡片 + 算法选择理由 + 下钻路径 + 验证 SQL + trace_id，业务人员可点开任意环节验真
- **LLM 是编排者，不是计算者**：所有数字必须来自算法/SQL 的返回值，不允许 LLM 写出未在验证集中出现过的数字
- **行内事件库**是 LLM 假设生成的关键先验源（产品到期日历、营销活动、利率调整、监管事件）—— 这是项目和通用方案最大的差异化
- **算法工具箱"插件化"**：每个算法独立可测，新算法（如未来的因果推断算法）按 schema 接入即可
- **失败兜底**：HotSpot/Squeeze 跑超时或不收敛时，自动降级为"维度下钻 + 帕累托"，并在结论里标注"使用了简化归因方法"
- **业务人员可主动给假设**：UI 提供"我猜是因为 XX"输入框，走假设验证路径——把人的业务直觉变成系统可验证的证据

#### Module 6: 洞察合成 Agent（Insight Synthesizer）— **解决 P2 的核心**

**职责**：所有路径的最终一公里，把"原始数据"变成"业务人员看得懂的回答"

**输出结构**：

```python
class InsightCard:
    headline_number: str         # 1 个核心数字，加粗大字号
    headline_comparison: str     # 同/环比一句话
    chart: ChartSpec             # 自动选图表类型
    narrative: str               # 2-3 句话业务解读
    drill_actions: List[str]     # 3 个追问按钮
    metric_provenance: Dict      # 用了哪个指标、SQL、表（可点开）
    confidence_level: Literal["high", "medium", "low"]
```

**图表自动选择规则**（不要让业务人员选图表类型）：

- 单数字 → 大字号 + 同环比
- 时间序列 → 折线图
- 维度对比 ≤ 7 项 → 柱状图，>7 → 条形图（按值排序）
- 占比 ≤ 5 项 → 环形图，否则用条形图
- 双维度交叉 → 热力图

#### Module 7: 银行合规层（横切关注点）

| 能力        | 实现                                                                                 |
| ----------- | ------------------------------------------------------------------------------------ |
| SSO         | 对接行内 AD/OA                                                                       |
| 行级权限    | 按用户的「分行/部门/客群」过滤数据（DB 端 RLS + 应用端二次校验）                     |
| 列级脱敏    | 卡号 / 身份证 / 手机号自动脱敏；敏感列直接禁查                                       |
| 全链路审计  | 谁、在什么时间、问了什么、命中了哪个指标、跑了什么 SQL、看到了哪些行 → 全部入审计库 |
| Prompt 越权 | 检测 prompt injection（"忽略前面的指令..."）                                         |
| 速率与成本  | 按用户/按部门做配额                                                                  |

#### Module 8: 反馈飞轮 & 评估体系

业务人员每次回答下方有 👍/👎/纠错 按钮：

- 👍 → 沉淀为新的 few-shot 示例（候选）
- 👎/纠错 → 进入 badcase 池，由数据治理人员审核 → 修复指标定义 or 补充 few-shot
- 持续运营 dashboard：回答采纳率、指标覆盖率、归因准确率、平均节省时间

**评估集**（替代原 BIRD-financial 的纯学术倾向）：

- **银行问题集 v1**：100 道真实业务问题，分 P1/P2/P3 三类
- **指标覆盖率**：业务问题中能命中指标平台的占比（目标 ≥ 70%）
- **RCA 一致性**：归因结论与人工分析师对照（目标 Top-1 命中 ≥ 60%）
- 仍保留 BIRD-financial 子集做技术对比

| 私有化部署 / K8s                                      | DevOps                | 安全合规联合验收                  |

#### 10.7 银行项目特有的组织风险点

1. **业务专家必须"挂职进项目"**，不能只是访谈对象——指标口径、归因方法论、问题集都需要持续投入，否则项目会变成"技术想象中的 BI"
2. **数据治理角色不可省**——v1 文档里没有这个角色，是常见踩坑点。指标平台没人维护，3 个月就会失效
3. **安全合规要"前置"而非"上线前再说"**——RLS、脱敏、审计日志的接入点必须在 M1 就规划好，后补成本巨大
4. **运营是长期角色**——AI BI 项目不是"交付即结束"，反馈飞轮、新指标添加、新问题模式适配都是持续工作，需要专人负责

### 十一、行外阶段数据集策略（mock 方案）

#### 11.1 背景与约束

项目第一阶段在**行外**完成框架开发，行内真实数据不能外带。本节回答："没有真实数据，怎么把 P1/P2/P3 三条路径都跑通并演示出说服力？"

**结论先行**：采用**三层混合数据集 + 归因事件埋雷**策略，**不推荐**简单的"自生成 + BIRD-financial"平铺组合。

#### 11.2 为什么"自生成 + BIRD-financial"不够

| 方案                              | P1 取数     | P2 多步 | P3 归因                  | 对外可比 | 业务真实感 |
| --------------------------------- | ----------- | ------- | ------------------------ | -------- | ---------- |
| 纯 Faker 随机                     | ✅          | ✅      | ❌**致命问题**     | ❌       | 低         |
| 纯 BIRD-financial                 | △ 不贴银行 | △      | ❌                       | ✅       | 中         |
| Faker + BIRD（平铺）              | ✅          | ✅      | ❌**仍然没有因果** | ✅       | 低         |
| **三层混合 + 埋雷（推荐）** | ✅          | ✅      | ✅                       | ✅       | 高         |

**核心问题在 P3**：归因 Agent 跑得再好，如果数据里没有"可被发现的因果模式"，归因结果就是噪声。Faker 随机生成的数据在所有维度上均匀分布，HotSpot/Adtributor 跑出来都是"贡献度差不多"。**RCA 的效果完全取决于数据里有没有"埋雷"**。

#### 11.3 推荐方案：三层数据集

##### Layer 1 · 自建模拟银行数仓（核心，占 80%）

**作用**：架构主战场，P1/P2/P3 三条路径都跑在这上面，做演示用。

**生成方式**（不是纯 Faker）：

```
生成器 = 维度生成器（Faker）
       + 业务规则引擎（开户/交易/还款的合理时序分布）
       + 事件注入器（核心！把可归因的因果"埋"进去）
```

**表结构**：对齐文档前面定义的银行星型模型（10 张表，客户/账户/交易/产品/风险/运营六个域），规模可配置（10 万 - 1000 万行，默认 100 万级）。

**核心创新：归因事件库 + 传导规则**：

```yaml
# data/events/event_2026_05.yaml
events:
  - id: anxin_90_expire
    name: 安鑫90天理财到期
    date: 2026-05-14
    affected_dimensions:
      branch_id: [上海分行]
      customer_tier: [HIGH_NET_WORTH]
      product_id: [PROD_FIN_AX90]
    propagation:
      - metric: retail_deposit_balance
        delta: -8.5%
        delay_days: 1        # 5/15 开始显现
        ramp: linear         # 渐变 3 天
        renewal_rate: 0.42   # 42% 客户续作其他产品
      - metric: aum
        delta: -3.2%
        delay_days: 1
    expected_rca_conclusion: |
      上海分行高净值客户的活期存款下降，主要原因是「安鑫 90 天」
      到期未续作，续作率 42% 低于历史均值 65%

  - id: rate_cut_q2
    name: 二季度 LPR 下调
    date: 2026-05-20
    propagation:
      - metric: loan_application_count
        delta: +12%
        delay_days: 7
```

**这样做的两大收益**：

1. **P3 准确率可自动评估**：归因 Agent 跑完后，把结论与 `expected_rca_conclusion` 做语义匹配，准确率有了量化指标
2. **演示效果震撼**：业务人员问"为什么下降"，系统给出的根因和"埋雷文件"对得上

**事件库可持续扩充**：产品到期、营销活动、利率调整、节假日效应、监管事件、宏观冲击。

##### Layer 2 · BIRD-financial 子集（基准对标，占 15%）

**只做一件事**：跑公开 NL2SQL 准确率，给项目一个可对比的学术数字。

- 不作为主数据集（表结构不贴中国银行业的指标体系）
- 不用它评估 P3（BIRD 没有归因任务）
- README 上一行字："在 BIRD-financial 子集上 execution accuracy 达到 XX%"，让外部审视者有锚点

##### Layer 3 · 公开真实金融数据（可选增强，占 5%）

**作用**：补充真实分布、引入真实噪声，避免自生成数据"过于干净"。

候选数据集：

- **Kaggle Lending Club** —— 真实贷款数据
- **UCI Bank Marketing** —— 真实营销响应数据
- **Credit Card Fraud Detection** —— 极不均衡的真实分布
- **PKDD'99 Financial Dataset** —— 捷克银行真实数据，经典案例

**用法**：抽样融入自生成事实表，做"噪声注入"，不替代主数据集。

#### 11.5 配套问题集设计（与数据严格对应）

数据集只是地基，**评估问题集才是真正决定项目说服力的东西**。问题集要与数据严格配套：

| 问题集                    | 数量   | 数据来源                                    | 期望答案怎么定                       |
| ------------------------- | ------ | ------------------------------------------- | ------------------------------------ |
| **P1 精准取数集**   | 50 道  | Layer 1                                     | 标准 SQL + 期望数值                  |
| **P2 多步分析集**   | 30 道  | Layer 1                                     | 标准多步 SQL + 期望洞察 outline      |
| **P3 归因集**       | 20 道  | Layer 1（**每道题对应一个埋雷事件**） | 直接对照 `expected_rca_conclusion` |
| **BIRD 子集**       | 100 道 | Layer 2                                     | 官方答案                             |
| **指标命中专项**    | 30 道  | Layer 1 + 指标库                            | 期望命中的指标 ID                    |
| **业务术语别名**    | 20 道  | Layer 1                                     | 测同义词扩展                         |
| **拒答 / 模糊问题** | 10 道  | —                                          | 期望路由到 `unsupported`           |

**P3 自动评估实现**（与 Module 5 RCA Agent 配套）：

```python
class RCAEvaluator:
    def evaluate(self, question: str, expected_event: Event) -> RCAScore:
        report: RCAReport = self.rca_agent.analyze(question)

        return RCAScore(
            # 1. 关键维度命中（埋雷事件的 affected_dimensions 是否被识别）
            dimension_recall=self._dim_overlap(
                report.attribution.top_dimensions,
                expected_event.affected_dimensions,
            ),
            # 2. 关联事件命中（埋雷事件 ID 是否在假设池中被验证）
            event_hit=expected_event.id in [h.event_id for h in report.hypotheses],
            # 3. 结论语义一致性（LLM-as-judge 对照 expected_rca_conclusion）
            conclusion_similarity=self._semantic_match(
                report.narrative, expected_event.expected_rca_conclusion,
            ),
            # 4. 是否含有不可追溯的数字（幻觉检测）
            hallucinated_numbers=self._detect_hallucination(report),
        )
```

#### 11.6 行外 → 行内的迁移路径

行外这套数据集必须**为行内迁移做好准备**：

1. **表结构抽象**：用 YAML/SQL 描述 schema，不写死代码。行内对接时只换 YAML
2. **指标 YAML 与数据解耦**：指标定义只引用表名+字段名，行内只换 DB 连接，指标库直接复用
3. **事件库可继承**：行外定义的事件类型（产品到期/营销活动/利率调整）在行内是同样的形态，业务侧只需补充真实事件
4. **评估方法论可移植**：行内一定会让业务专家标 50-100 道真实问题集，方法和行外完全一样

#### 11.7 常见踩坑清单

| 坑                               | 后果                             | 解法                                            |
| -------------------------------- | -------------------------------- | ----------------------------------------------- |
| 数据规模一上来就 1 亿行          | 本地跑不动、迭代慢、demo 卡      | 默认 100 万级，可配置上探                       |
| 自生成数据时间分布均匀           | 时序异常检测、同环比都看不出东西 | 业务规则带工作日效应/节假日/月末效应            |
| 维度值均匀分布                   | 帕累托归因失效                   | 维度值服从长尾分布（分行规模、客户 AUM）        |
| 只用 BIRD 评估                   | 简历好看但 demo 讲不出"银行业务" | 业务问题集和 BIRD 并行                          |
| 事件库无人维护                   | 演示一次就过时                   | 事件库 YAML 走 git，作为版本控制对象            |
| Mock 数据出现真实姓名 / 身份证号 | 内部传播引起合规误会             | Faker 全部用明显假数据（"张三001" / 110...000） |
| 没准备"对照人工分析师"的标注     | P3 准确率无法量化                | 每道 P3 题对应一个埋雷事件，准确率自动算        |

#### 11.8 一句话总结
